    Rebuild the Core - Progress on the Server Rewrite

    Rebuild the entire MCSR Ranked backend from the scratch

    Hello, everyone! We’re so glad with finally I can post about this publicly.
    We know that content updates have been somewhat lacking aside from the recent replay updates, and we believe you have noticed this as well.

    In the background, We’ve been putting so much effort into reinsfrastructuring the entire MCSR Ranked backend(the server).
    Now, we will explain why we have to do that, what’s going to be changed, and when it will happen.

    Problems of current server infrastructure

    The backend code for MCSR Ranked began to be rewritten in late 2022. Wow, it’s already been nearly 4 years.
    During this process, I (RedLime) wrote 99% of the backend code, and you might be surprised, this was my first attempt at a WebSocket project.
    In short, before starting this project, I had absolutely no idea how WebSocket worked, and I literally started learning about it as I began the project.
    I also lacked a significant amount of technical knowledge regarding various backends.

    However, with a lot of help of Google search, I made the first version of the backend, and surprisingly, the server started working!
    But, this initial backend was not designed to accommodate thousands of players playing simultaneously.
    Because We never even imagined that the project would eventually reach thousands of concurrent users. It was literally our fashion project.

    Fast forward some years later, several issues began to surface.
    From 2023 to 2024, there were a few performance issues on the server, but since these were primarily database optimization problems, they could be fixed easily. However, from late 2025 to early 2026, a massive influx of players began all at once due to the Tubbo’s Midoffs and spectacular plays of Ludwig. The average number of concurrent users jumped more than 10x in an instant, which was completely unexpected. As a result, various structural problems with the backend design began to be discovered.

    Memory usage and performance with Database

    We had used a No-SQL database. because the initial MCSR Ranked backend required various changes, which facilitates data structure modifications.
    However, at this point, the database’s structure become relatively stabilized, and various problems also arised due to the inherent limitations of No-SQL.
    Memory usages and performance degration were particularly severe. Specifically, as the number of matches and users increased, memory began to occupy up to 50% of the current server’s total memory, and is still increasing.
    And also, due to the limit of No-SQL, performance lags significantly when using queries that link multiple tables for analysis. Consequently, it was difficult to implement various analytical functions within the server.
    This naturally became a major obstacle to adding new features to the server and established a critical challenge that needed to be resolved.

    Everything is in single core/process

    Similarly, another issue has appeared that was not a problem in the past but has emerged as the number of users increased.
    Currently, the MCSR Ranked backend bundles all services into a single process. This includes the game server, API, Discord bot, website proxy, and other services.
    Therefore, if even one of these elements has a significant heavy performance load or an error that causes the process to crash, the entire server crashes with it.

    Yes, the situations shown in these videos were caused precisely by this problem.

    Another problem is that since all of this works within a single process, the server’s full CPU performance cannot be utilized. Although the server currently has multiple cores, the game server process was using only a single core. This resulted in a waste of performance.
    Fortunately, since the Database and proxy processing systems were using multiple cores, it was not a complete waste.

    Hard to hotfix for specific element

    This issue is directly related to the single process problem mentioned above.
    If a minor issue occurred in the server logic requiring a hotfix, or if changes were needed to the API, the entire server had to be restarted unconditionally. This was the case even for a single line of code change.

    This is important because it means that any ongoing Ranked Mode gameplay must also be suspended. Basically, it takes at least an hour to inspect and restart the entire server. We have to wait for ongoing matches to finish, apply the patch, and then perform a final check of the changes.
    While this would be perfectly reasonable for large-scale updates, the same steps are required even to apply a single line of code change.
    Since such long downtime is not ideal, a method was needed to manage each process more efficiently.

    The new infrastructure

    To resolve all these issues and ensure scalability to accommodate more players in the future, we have built a new server infrastructure.

    We have separated each major feature into a separate process: The game server, API, and Discord bot, to ensure that applying changes does not affect other services.
    Furthermore, because the processes are separated, each service can utilize an entire single core, which grants significantly more CPU performance available to the service.

    Additionally, the API and Game Server can also be split into multiple processes. This allows us to handle increased demand in the future by simply adding more processes, while also making the deployment of updates much easier.
    In particular, if changes are required for the Game Server, we create a new process with the updated changes and prevent access to the existing process, enabling the changes to be applied to players sequentially.

    The database has also been migrated to a SQL-based architecture. This allows for more efficient memory usage, smaller data sizes, and improved performance.
    While it is difficult to go into specific details about this, just know a lot of effort has been put into it. 🫠

    Future Plans & New Features

    In fact, We’ve already started the private test with this new server infrastructure! This update is planned around the near future if we don’t have any major issue while in the private testing phase, and we expect it around this December or start of Season 13!

    Also, we’ve implemented some new features for testing the new server performance already:

    • Match API bulk files for download and every match API data in a specific season.
    • Fastest time leaderboard with Country filter.

    After this update, we will start to work on some wanted features:

    • Pronouns
    • New Seed Rush Mode
    • Notification of Report Reviewed
    • Cosmetics Update

    Some tasks applied only in the client, such as standardization or UI rework among other things, haven’t been included in this list. Of course, those will also be worked on.

    Postscript

    We would like to take this opportunity to apologize for the updates that have been delayed due to the work on this massive undertaking.
    The features mentioned earlier will be implemented after the deployment of the server rewrite, and we look forward to introducing even more contents to MCSR Ranked in 2027.
    Thank you for your patience.

    I would also like to give thanks to Roco and Eva (xyzeva) for their contributions to this update.
    With Eva, she provided the concepts and demo architecture for this new infrastructure. Without her, this project wouldn’t have been possible.
    Roco also helped an entire rewrite process, with her efforts, we are on track to complete this work within this year.
